**Анализ взаимодействия (на примере пакета № 44):**

**Структура заголовка TCP:**
* **Source Port:** `56975` — эфемерный порт клиента (выбран ОС автоматически).
* **Destination Port:** `666` — порт сервера (задан в коде TCPServer.java).
* **Sequence Number:** `162` (relative sequence number) — номер первого байта данных в этом сегменте относительно начала соединения.
* **Acknowledgment Number:** `70` (relative ack number) — номер следующего ожидаемого байта от сервера (подтверждение получения 69 байт).
* **Header Length:** `20 bytes (5)` — длина заголовка TCP (5 слов по 4 байта).
* **Flags:** `0x010 (ACK)` — флаг подтверждения получения данных.
* **Window Size:** `255` — размер окна приема (сколько байт клиент готов принять без подтверждения).
* **Checksum:** `0x39b8 [unverified]` — контрольная сумма (не проверяется на loopback интерфейсе).
* **Urgent Pointer:** `0` — указатель на срочные данные (не используется).

**Интерпретация полей:**
* **Source/Destination Port:** Идентифицируют приложения-отправитель и получатель.
* **Sequence Number:** Обеспечивает надежную доставку — получатель знает, в каком порядке собирать данные.
* **Acknowledgment Number:** Подтверждает получение данных — отправитель знает, какие данные дошли.
* **Flags:** Управляют соединением (SYN — установка, ACK — подтверждение, FIN — завершение, RST — сброс).
* **Window Size:** Механизм управления потоком — предотвращает переполнение буфера получателя.

**Этапы TCP-сеанса:**
1. **Установка соединения (Three-way handshake):**
   * Клиент → Сервер: `[SYN]` Seq=0
   * Сервер → Клиент: `[SYN, ACK]` Seq=0, Ack=1
   * Клиент → Сервер: `[ACK]` Seq=1, Ack=1

2. **Передача данных:**
   * Клиент отправляет данные с флагом `[PSH, ACK]`
   * Сервер подтверждает получение `[ACK]`
   * Сервер отправляет ответ `[PSH, ACK]`

3. **Завершение соединения:**
   * Обмен флагами `[FIN, ACK]` (четырехэтапное закрытие)
   * Возможна отправка `[RST, ACK]` при резком закрытии сокета

* `Window Size` — нет управления потоком

Благодаря этому UDP обеспечивает минимальные накладные расходы и задержки, что делает его идеальным для:
* Потокового видео и аудио
* DNS-запросов
* Онлайн-игр
* Систем реального времени

8. Выполнить анализ ARP-протокола по примеру из методических

Ответ:
Запущен захват с фильтром `arp`. В списке пакетов обнаружен ARP-запрос от роутера.

**Анализ ARP-запроса (пакет № 26):**

**Структура пакета:**
* **Frame 26:** 60 bytes on wire (480 bits)
* **Ethernet II:**
  * Source: `TPLink_d6:97:46 (50:91:e3:d6:97:46)` — MAC-адрес роутера (отправитель запроса)
  * Destination: `Broadcast (ff:ff:ff:ff:ff:ff)` — широковещательный адрес (запрос всем устройствам в сети)
* **Address Resolution Protocol (request):**
  * `Hardware type: Ethernet (1)` — тип аппаратного адреса (Ethernet)
  * `Protocol type: IPv4 (0x0800)` — тип протокола сетевого уровня (IPv4)
  * `Hardware size: 6` — размер MAC-адреса (6 байт)
  * `Protocol size: 4` — размер IP-адреса (4 байта)
  * `Opcode: request (1)` — тип сообщения «запрос»
  * `Sender MAC address: TPLink_d6:97:46 (50:91:e3:d6:97:46)` — MAC-адрес роутера
  * `Sender IP address: 192.168.0.1` — IP-адрес роутера
  * `Target MAC address: 00:00:00:00:00:00` — поле пустое (MAC неизвестен)
  * `Target IP address: 192.168.0.101` — IP-адрес целевого устройства

**Интерпретация:**
Роутер (192.168.0.1) отправляет широковещательный ARP-запрос всем устройствам в локальной сети, чтобы узнать MAC-адрес устройства с IP-адресом 192.168.0.101. Поле `Target MAC address` заполнено нулями, так как искомый адрес еще неизвестен.

**Принцип работы ARP:**
1. Узел проверяет ARP-кэш на наличие нужной записи.
2. Если записи нет, отправляется широковещательный ARP-запрос (`ff:ff:ff:ff:ff:ff`).
3. Все устройства в сети получают запрос, но отвечает только то, чей IP совпадает с `Target IP address`.
4. Ответ (ARP Reply) отправляется напрямую на MAC-адрес запросившего устройства.
5. Запись сохраняется в ARP-кэше на 2-10 минут.
